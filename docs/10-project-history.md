# 从首次联调到综合上位机的开发记录

本文按问题链路记录项目为何形成当前结构。它用于交接设计背景；最新命令和接口仍以
各模块专题文档及源码为准。

## 阶段 1：CR5 ROS 2 环境建立

起点是 Ubuntu 22.04、ROS 2 Humble 和 CR5 二次开发。选择设备方的
`DOBOT_6Axis_ROS2_V3`，原因是它面向六轴 CR/Nova 系列并提供 V3 TCP 端口、
ROS 服务、URDF、RViz 和 MoveIt 包。

首次 `source ~/dobot_ws/install/setup.bash` 失败，是因为工作空间尚未构建。随后补齐
`joint_state_publisher_gui`、`controller_manager`、ros2_control 和 MoveIt 依赖，
完成：

- `dobot_rviz` 模型与关节滑块；
- `cr5_moveit demo.launch.py` 离线规划；
- V3 工作空间正常 colcon 构建。

这一阶段确认不需要为 ROS 2 单独创建 Conda 环境，反而应使用 Humble 对应的系统
Python 3.10，避免 Conda Python 和二进制 ROS 包 ABI 冲突。

## 阶段 2：真机网络与三端口

先后验证过 CR5 Wi-Fi `192.168.1.6` 和有线控制地址。核心判断从“是否 ping 通”改为
“路由是否正确、29999/30003/30004 是否同时可用”。原因是 ICMP 可能被丢弃，而
TCP 服务仍正常；反过来，VPN/TUN 也可能让端口探测产生假阳性。

成功 bringup 的判据是：

- Dashboard 29999；
- 运动 30003；
- 反馈 30004；
- ROS `RobotMode`、`GetAngle`、`GetPose` 都返回真实值。

同时明确不能让 ROS、DobotStudio 和 `nc` 并发占用控制连接。

## 阶段 3：模式、报警与旧驱动缺陷

联调中出现过：

- 模式 9 且 `GetErrorID()` 返回多组控制器/关节报警；
- 清警 `res=0` 后模式仍是 9，因为报警根因未消除；
- 29999 被控制器重置，bringup 节点直接退出；
- 30004 初次连接失败后 `PublisherNode` 没有 `feed_v`，定时器触发
  `AttributeError`；
- ROS `GetErrorID` 回调只填了 `res`，没有填 `error_id`；
- `/joint_states_robot` 有时全零，根因是反馈链路而不是机械臂真实角度。

因此修复了连接的原子建立、异常传播、定时重连、完整反馈帧重组、服务断线保护和
报警字段解析。特别约束：运动 socket 出错后不自动重发运动指令。

## 阶段 4：拖动、安全保护与取点

项目需要拖动示教。开始时 `StartDrag res=-1`，且电子皮肤触发时出现 `-3`。这促使
程序区分：

- `SetCollisionLevel`：本体碰撞检测；
- `SetSafeSkin`：电子皮肤；
- `StartDrag/StopDrag`：拖动状态。

原 V3 ROS 包缺少完整 SafeSkin 接口，因此新增服务和测试。GUI 默认保持 SafeSkin
开启，只允许操作员显式选择临时关闭；进入拖动失败、退出和关闭 GUI 都尝试恢复。

取点从“复制终端输出”升级为原子保存：同一点位包含六轴角、Tool0 位姿，后续再加入
相机图和采集元数据。保存前后检查关节漂移，避免机械臂仍在移动时生成错误配对。

## 阶段 5：点位运动与 Sync 卡死

早期点间程序下发 `JointMovJ` 后调用 `Sync`，120 秒后客户端超时。日志证明在此期间
关节角一直停在起点，`Sync` 的服务端则卡在 socket `recv()`，并占住单线程 bringup
节点的所有服务。

最终方案彻底移除 `Sync`：

- 先确认模式 5 和当前点等于指定起点；
- 下发低速 `JointMovJ`；
- 轮询 `GetAngle` 和 `RobotMode`；
- 识别未启动、报警、暂停、提前停止和总超时；
- 到位并连续稳定、模式恢复 5 才成功。

这套状态机同时用于 CLI `dobot_point_manager` 和 GUI。

## 阶段 6：DH-AG95 与任务队列

确定末端 RS485 专用于 DH-AG95 后，通过控制器内部
`ModbusCreate(127.0.0.1,60000,1,1)` 建立 RTU 通道，补全并校验
`SetHoldRegs/GetHoldRegs`。

上位机加入初始化、夹持力、位置、开闭和反馈等待。随后建立版本化任务队列，支持：

1. 移动到 P1；
2. 夹爪闭合指定百分比；
3. 等待；
4. 移动到 P2；
5. 继续其他夹爪动作。

队列严格串行，任一步失败都不会继续执行后续步骤。

## 阶段 7：SC3000 标准协议取图

由于 Linux SDK 不明确且最终目标是 Ubuntu/ROS 2，选择绕过 Windows SCMVS 手动
操作，以标准协议实现：

- Ubuntu 内嵌 FTP Server；
- Modbus TCP 触发相机；
- 等待上传完整的新 JPG；
- 实时预览用 `/dev/shm`，显示后删除；
- 正式采集图与机器人状态写入同一目录。

这条链路先在独立脚本验证，之后封装进综合 GUI。目标为 5 FPS，但实际速率由相机
任务和 FTP 周期决定。

## 阶段 8：内参、AprilTag 和手眼标定

使用 22 组棋盘数据，参数为 7×5 内角点、11.2 mm。对标准五参数和多种受约束畸变
模型做逐图误差及留一法比较，最终选用稳定的 `radial-k1` 模型。

随后使用实测 58.5 mm `tag36h11` AprilTag，通过 IPPE Square + LM 得到相机坐标
XYZ/RPY。早期把标签尺寸写成 5.85 mm 时，坐标尺度也随之错误 10 倍，这成为部署
检查项。

眼在手上标定采用前 20 组，排除后两组疑似偏移数据，比较五种 OpenCV 算法并选择
Park。再用独立 V6～V12 数据验证固定标签在基座坐标中的一致性。最终把变换加入
GUI，使实时结果同时显示：

- OpenCV 相机坐标；
- CR5 User0/基座坐标。

仍未自动完成的是“标签到实际抓取点”的工装固定偏移；在加入自动抓取前必须单独
标定并设置运动边界。

## 阶段 9：SEER AGV 迁移与统一集成

阅读 SEER 交接包和完整协议后，把 AGV 源码迁入同一 ROS 工作空间，并建立两层：

- `seer_agv_driver`：唯一 TCP 所有者；
- `seer_agv_msgs`：GUI 使用的类型化服务。

第一轮实现状态、电池、报警、定位、车体模型、地图 Marker、站点导航和低速点动；
安全门发现 Robokit 3.4.4.6 的 `reloc_status=3` 是“等待操作员确认”，因此禁止
导航/点动，之后安全封装 API 2003。

第二轮补上：

- GUI 实时地图和车体姿态；
- 4011 刷新、2022 加载地图；
- 2002 重定位、2004 取消；
- 地图点选初值；
- 定位后再次人工确认；
- 修复前进按钮的具体按键状态判断；
- 同时显示指令速度和实测速度；
- 识别前向 `slowed` 安全区拦截；
- 启动器的有线载波/路由检查，消除 TUN 假在线。

## 阶段 10：当前边界

已完成的是设备连通、人工安全操作、数据采集、视觉位姿、点位/夹爪队列和 AGV
地图导航基础能力。正式生产使用前仍需：

- 按实际末端结构重新确认负载、重心和 Tool 坐标；
- 每台相机独立内参和手眼标定；
- 标定 `tag_T_grasp`；
- 在受控现场完成 AGV 前进、地图切换、重定位和站点导航验收；
- 增加工作空间/自碰撞/视觉置信度约束后再考虑自动抓取；
- 根据部署单位的安全评估和变更管理流程审查全部运动功能。

## 阶段 11：基于 AprilTag 的 AGV 到站纠偏队列

为降低 AGV 航点重复定位误差对预先示教机械臂动作的影响，任务队列加入两阶段
视觉纠偏：先在宽视野观察点对固定标签连续测量，得到
`B_now_T_tag × inverse(B_ref_T_tag)`；随后将这一完整 6D 变换应用到多个已示教
Tool0 目标。

同一队列也加入 `AGV导航到航点` 步骤。导航请求被接受后仍持续等待 ROS 发布的
新导航状态，只有确认完成才允许进入观察点和机械臂动作；失败、取消、定位丢失或
超时均停止后续步骤。

接近点可使用笛卡尔 `MovJ`，按压和撤回可使用低速 `MovL`。程序对参考标签、
重投影误差、多帧离散、最大平移/旋转、RobotMode 和最终到位状态做失败关闭检查；
任一步失败都不会继续按压。此能力完成了离线单元测试和构建验证，但仍须按“只测量
预览 → 接近点 → 空行程按压 → 实际按钮”的顺序完成现场低速验收。
